# 黄金结果与工程证据核验

先确定“比较的是什么”，再决定改参考模型、测试脚本还是实现。不能为了得到 PASS 临时修改阈值、放宽误差或改黄金结果。

## 工作顺序

1. 向当前代码和接口文档核实数据类型、形状、字节序、饱和/舍入规则、边界、输出是幅值还是二值。阈值值与 `>` / `>=` 必须逐项一致。有并列最大值时检查选择次序。
2. 冻结一份输入，同时保存主机和硬件输出。元数据与完整输出分别比对；元数据相同不能替代逐像素/逐采样点检查。
3. 用 `scripts/compare_binary.py` 比较裸二进制。只有契约明确要求时才能用 `--threshold` 转换参考幅值；实际输出不做这种转换。浮点容差必须来自算法精度要求。
4. 保留失败数和首批坐标。先按边界、位序、符号、饱和、阈值、帧尾排查，再考虑硬件逻辑缺陷。
5. 将源文件、部署产物、报告和配置归入同一个版本标识，用 `scripts/collect_evidence.py` 记录身份和结果。哈希证明文件身份，不证明源码到 bitstream 的生成关系。
6. 性能只对同一输入、同一计时边界配对。分开记录 DMA 窗口、完整调用、采集、渲染；不拿历史 CPU 样本除以当前 FPGA 帧。
7. 明确证据层级：本地脚本测试、仿真、实现报告、上板回归各自能证明什么。缺失数据写 UNKNOWN，不补成 0，不用资源利用率推导性能或能效优势。

用法、格式边界及实际问题来源见 [README.md](README.md)。首次复用先运行其中的合成示例，核对直接比对为 FAIL、按明示阈值转换后为 PASS，再接入自己的数据。

## 交给模型的提示词模板

> 以下是算法契约、同一输入的参考输出与硬件输出，以及当前版本实现报告。请先列出二者的数据语义、数值规则和计时边界；指出不具备可比性的项目。给出最小核验命令，再按可复现的首个差异定位。不要为了通过测试修改算法或黄金文件。报告中将“已测”“未测”“无法确定”分开，并标注每项数据的文件来源与版本。
